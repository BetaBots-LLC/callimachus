OpenCode 2's sessions, project memory in the editor sidebar, and a Codex plugin.

- **OpenCode 2's sessions are indexed.** OpenCode v2 keeps sessions in new tables (`session_v2`, `session_message` and, since v2.2.2, `session_part`) of the same `opencode.db`, and the indexer read only the v1 tables: sessions started under v2 never showed up, and on a fresh v2 install (no v1 tables at all) every OpenCode pass failed. The indexer now checks which tables the database holds before reading any of them. It reads the v2 tables when they are there, and the v1 tables only for the sessions OpenCode's background copy has not taken yet (the copy keeps the ids, so a copied session updates its existing thread instead of appearing twice) and for those OpenCode 1.x wrote after the copy. v1 installs (OpenCode 1.x is still the npm `latest`) read as before.
- **What a v2 session indexes.** Your prompts and the assistant's text, each step's text in the order OpenCode's own history reader merges it. Subagent sessions are marked as subagents; a fork is not one, and the history a fork copies from its parent is not billed a second time (it is billed in the fork when the parent was deleted before Callimachus ever read it). Token usage and model come from each assistant step, never from the session totals on top. Tool output, reasoning, attachments, shell / skill / compaction text and notices are not indexed. A row holding a value of an unexpected type is skipped and counted instead of failing the whole pass.
- **New OpenCode turns show up before OpenCode checkpoints.** OpenCode writes in WAL mode, so a new turn sits in `opencode.db-wal` first: the change check now covers that file too, and a pass that can only read the main file while the WAL holds data reads nothing and tries again on the next one.
- **A Memory view in the VS Code extension.** Under History, the extension lists what Callimachus remembers about the open folder's project: its decisions, gotchas and open TODOs (what `cal memory` prints there; a git worktree shows its main repository's memory) and its recurring errors with the commit recorded for each and its playbook (from `cal issues`, mined only when you expand that group, which can take several seconds on a large index; like `cal issues`, it also includes projects whose path contains this one, and it is left out for your home folder or a folder above it). A fact shows when it was decided and which agent's session it came from, with an icon when it is pinned, disputed or flagged as stale or wrong; click a fact, an error or its fix to open the session it came from. Each group lists up to 40 facts and reads `40+` when there may be more. The view only reads (pin, edit and hide stay in the app) and asks again when you press Refresh.
- **The view says what is wrong.** When `cal` is missing, there is no index yet, the index is busy, is older than your `cal` or is halfway through a restore, it says what to do in the app instead of showing an error. The extension also recognizes `cal`'s "no index" message now, which it missed before, so the sidebar's download prompt appears instead of the raw error, and a workspace folder that no longer exists is reported as that instead of as a missing `cal`.
- **Codex plugin (experimental).** `plugins/codex` brings the `recall` skill, the MCP server (`npx -y callimachus-mcp@<version>`, pinned to the release), the SessionStart, PreCompact and SessionEnd memory hooks and a `cal index --if-stale` hook to Codex without the desktop app's Settings, as the Claude Code and Cursor plugins do. It is built from Codex's plugin loader source (tag rust-v0.167.0) and the plugins bundled with Codex, and is not yet install-tested; Codex runs a plugin's hooks only after you trust them in `/hooks`. Add the marketplace with `codex plugin marketplace add BetaBots-LLC/callimachus` and install it in the ChatGPT desktop app. The hooks run `cal` from the app at this release or later and stay silent with an older one. macOS and Linux only; on Windows, use Settings > Agents.
- **Codex now offers the Codex plugin from this repository, not the Claude Code one.** The new `.agents/plugins/marketplace.json` is the first catalog Codex reads in a repository, ahead of `.claude-plugin/marketplace.json`. Anyone who added this repository to Codex as a marketplace before gets the Codex plugin listed on their next marketplace upgrade instead of the Claude Code plugin, whose hooks were written for Claude Code. Claude Code and Cursor read their own catalogs as before.
- **The app and the Codex plugin share the work.** While the plugin is enabled in Codex's `config.toml` and installed in Codex, the app removes its own `[mcp_servers.callimachus]` entry there, so one server starts, and puts it back as it was (with any keys you had added) once the plugin is off; an entry you add back yourself in between stays. The app keeps its own Codex hooks (`~/.codex/hooks.json`) either way. Once you trust the plugin's, Codex runs both for every event, so the memory is injected once and the session snapshotted once: while the plugin is enabled, trusted or not, the first of the app's and the plugin's runs of an event claims it for 5 seconds, so a second clear or compaction of one session within 5 seconds injects nothing. Without the plugin each hook runs exactly as before and writes no claim.
- **Hooks stay quiet under Devin CLI** (from Devin CLI's documentation, not yet tested with Devin). Devin's docs say it loads the hooks in `~/.claude/settings.json` and sends payloads without a `transcript_path`, so its session end could open the index writable and, with memory and auto-distill on, queue the Devin session as a Claude Code one that never resolves. With `DEVIN_PROJECT_DIR` set and no transcript in the payload, `cal session-end`, `cal snapshot-hook`, `cal recall-now` and `cal recall-error` now exit before opening the index. Claude Code documents `transcript_path` in every hook payload, so a `DEVIN_PROJECT_DIR` leaked into a Claude Code session changes nothing.
- **Code comments are not recurring errors.** A `//` or `/*` comment line, bare, in a diff or behind the `path:line:` prefix grep prints, no longer counts as an error, whatever words it holds.

The OpenCode reader is built from OpenCode's source at v2.2.7 and tested on databases made from its table definitions; it has not yet run against a live v2 install. Channel databases (`opencode-<channel>.db`), `OPENCODE_DB` and Kilo CLI's `kilo.db` are not read.
