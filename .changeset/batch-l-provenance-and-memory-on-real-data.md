Recurring errors that are errors, memory that follows your work, a TODO list of this project's work, and a place to review what agents did to memory.

- **Fewer false errors.** File content read with a line-number gutter (the Read tool, `cat -n`), source lines that only name an error variable (`error: err instanceof Error ? err.message : err`, `onError: (error) => ...`, `error: {`), a script's `echo "error: ..."` line and a Rust path such as `io::Error::new` no longer count as errors. A Python traceback counts as its exception line (`json.decoder.JSONDecodeError: Expecting value`), filed under the session's own files among its frames, instead of the `Traceback (most recent call last):` header every Python error shares, which was the most frequent "recurring error" on a large index.
- **Lists show errors that say what went wrong.** `cal issues`, `cal audit-pr`, the `recurring_issues` MCP tool, the report, Today and the Project page leave out generic lines (a bare `error:`, a CI exit code, cargo's `could not compile` and `test failed, to rerun pass`, a runner's `command exited`, `git apply`'s `patch does not apply`). They are still counted; `cal issues --all` lists them too.
- **Subagents count, once.** A Claude Code subagent's tool output now counts for the session that started it (its counts, project and fixes), so workflow-heavy repos see the errors their subagents hit; an error that the subagent's report then quotes back to its parent counts once. Today's "seen again" strip still reads top-level sessions only, to stay fast. Reading one repo's errors (`cal issues <project>`, `recurring_issues`) now reads its subagents' output too: on a measured index that took 0.45 s instead of 0.1 s for one repo and 1.1 s instead of 0.4 s for a larger one.
- **Failure playbooks leave the memory agents start with.** A playbook ("`<error>`: seen N times; fixed in `<sha>`") is recorded when a commit followed an error in the file it named. With subagents counted, a measured index went from 8 playbooks to 35 and they took every "Watch out for" line of one repo's session start, while the fix a playbook names is the commit after the error's latest sighting, not proof that the error stopped (28 of 34 were made within two days of it, and 4 of the errors were seen again afterwards). An unpinned playbook is now left out of the memory injected at session start and after a compaction, the AGENTS.md / CLAUDE.md block, the `project_memory` MCP tool, the resume block and the memory the distiller reads. It is still listed with the repo's gotchas on the Project page and in `cal memory` (after the others), `cal issues` and `recurring_issues` still return it with the fix, and the opt-in error-playbook hook still cites it. Pin one to have sessions start with it. Playbooks of generic errors and of lines the new rules no longer take are removed (pinned, edited and hidden ones are kept).
- **One re-mine.** Error signatures change, so the stored recurring errors are mined again once after the update, in the background like the regular refresh (8 seconds on a 5.4 GB index); until it lands, lists mine live with the new rules.
- **The files you are touching come first.** The SessionStart hook (and the refresher after a compaction) picked its decisions and gotchas by date, so in a repo with hundreds of facts the one about the file a session was about to change rarely made it. It now also looks at the files edited in the repo's 3 latest sessions (a session that only edited through subagents counts by theirs; sessions and files on the checked-out branch first, read from the checkout's `HEAD` without running git) and puts the facts that name one of those files right after your pinned ones, up to half of the lines your pinned facts leave (4 of each kind at session start). A fact names a file by its path (`core/src/export.rs`, also with a line range or an anchor after it), never by a bare `mod.rs`, nor by a `src/lib.rs` that every crate of a monorepo has. It helps where memory names files: in a replay of a measured index, 21 session starts had an earlier fact naming a file the session went on to edit, and that fact would have been injected in up to 13 of them, against 8 by date. A session start takes about a millisecond longer (16.5 to 17.6 ms). A repo without a session among the machine's recent ones keeps the date order. The app's "What agents see" preview and `cal hook --explain` show the same order; MCP `project_memory` and the AGENTS.md / CLAUDE.md block keep the date order.
- **Decisions as rules.** The distill prompt now asks for each decision as the rule that holds going forward ("Use X for Y", "Never Z") with its reason after a semicolon, instead of what the session did ("Fixed the layout shift by ..."). Existing facts keep their wording until a session is distilled again.
- **Checklists that name something.** An agent's `- [ ]` checklist line becomes a TODO only when it names a file, symbol, identifier, ticket or issue number. On a measured index, 76 of the 130 open TODOs were how-to steps written for the user (posting steps, profile fields, recording tips), and they are gone. TODO / FIXME markers and your own checklists are kept as before.
- **What agents left for later.** The items an agent lists under a heading or bold line such as "Follow-ups", "Known follow-ups, not in this PR", "Not done", "Deferred", "Remaining" or "Left to do" (at most 12 per message; not a list whose title says the work is done or names something that is not work, such as risks or questions; a bullet that only introduces nested items is read through to them) are now open TODOs in the app, `cal todos` and the MCP `list_open_todos` tool, marked with the extractor `followup` (the tool's schema is unchanged). Only a session's latest such list counts, and only one from the last 30 days: on the same index 87 of 90 such lists sat in the middle of their session, which went on for a median of 9 more turns, and nine tenths of their items were over a month old. The open items of an earlier list leave when a later one arrives (they stay in the transcript and in search), and a full reindex drops open follow-ups older than 30 days unless you pinned, edited or closed them. Once you reword a TODO of a session, that session's follow-up list stays as it is: its later lists are not added, and its open follow-ups stay until you close or hide them. A TODO marker or checklist line that repeats a follow-up stays when a later list leaves the follow-up out. "Next steps" lists are left out: they were mostly setup instructions.
- **A one-time re-judge.** After the update the app (or `cal watch`) re-judges the TODOs it already holds, once, in the background and in short batches that wait while a reindex or a semantic build runs: it deletes the open checklist TODOs the new rule rejects (one that a later TODO marker or your own checklist line repeats moves there instead) and adds each session's latest follow-up list from the last 30 days (31 items on that index, which went from 130 open TODOs to 85). A TODO you closed, pinned, hid or edited, one you or an agent recorded, and one from any other source are never touched.
- **Memory to review.** Today shows a "facts to review" button when there is something: facts an agent or a memory pass flagged stale or wrong, disputes nothing settled, and the facts agents replaced or recorded since you last opened the app, each with Keep, Undo or Hide; what you keep stays off the list, in the app and in the terminal. What agents replaced or recorded is listed first, and when more than 50 items wait the button reads "50+". `cal memory review [-p PROJECT] [--json]` prints the same list, read-only (flags and disputes until settled, replacements and recordings from the last 7 days); its `--json-version 1` output is published as `memory-review.v1.json`.
- **One Undo per fact.** Undo on a replaced fact (the Project page's Replaced list, or Today) now undoes every replacement of it at once, so a fact two sessions replaced comes back in one click, and stays back.
